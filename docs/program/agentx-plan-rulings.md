## Rulings on AutoClaw's open questions
1. **PR 7 signing source:** the vault signs ONLY from the stored proposal it re-reads itself; it recomputes the canonical hash and refuses on mismatch. The API passes {proposalId, userId, grantId} — never transaction fields. The vault must never become a signing oracle.
2. **PR 7 reconciliation:** the tx hash is computed locally from the signed bytes BEFORE broadcast and stored with the durable signed bytes. accepted_response_lost resolves by eth_getTransactionReceipt(that hash). A nonce probe (eth_getTransactionCount on from) is a secondary signal only. No block scanning.
3. **Nonce authority:** the proposal's nonce is authoritative. At sign time, chain nonce ≠ proposal nonce → typed refusal (stale_nonce); a fresh proposal is required. Never silently re-nonce a confirmed transaction.
4. **PR 8 fill gating:** align with the shipped PR #62 design — fill requires an owner-started run AND authorizeWalletRunOperation (valid unlock grant). The approval card is not a separate per-fill bypass.
5. **PR #29 capabilities:** server-defined typed capability set; the owner selects the allowed subset when creating the connection; the selection is STORED on the connection and enforced by call_connection. Derived defaults may pre-select, but enforcement is on the stored set.
6. **8h loop cap:** confirmed missing. Add a default per-turn hard cap (MAX_TOOL_CALLS_PER_TURN), env-overridable, set generously above the loop-guard thresholds.
7. **Contradiction gate (D2):** on a direct contradiction with a same-run tool result, block the reply and retry once with the contradiction surfaced to the model; if it repeats, stop with a typed reason — never ship the contradicted answer silently.
8. **Provenance (item 10):** a label on EVERY assistant reply showing the final serving model; the configured model + fallback chain go in the details/hover.
9. **Bot picker (item 11):** selection at NEW-CHAT creation (picker in the new-chat flow). Not in-thread retargeting — @mentions already exist for group chats. Untagged = orchestrator (Chief).
10. **VM status (item 12):** the InstaBox API DOES have it — GET https://api.instabox.sh/v1/machines/{id} (Bearer, the deployment's InstaBox key) returns state, runStartedAt, maxRunMinutes, cooldownUntil. The verifier's watcher uses it in production today. Surface: state + cooldownUntil (why/when back) + runStartedAt/maxRunMinutes (predicted pause).
11. **Drex workspace (item 13):** the workspace root is the bot's sandbox home (AGENT_HOME) on the team computer; botId → that root; deterministic local index; citations as path:line; NO Nace workspace sync in this item.
12. **Context purge (item 14):** at compaction / context-assembly points (per the design note), deterministic rules first, Drex scoring only for grey-zone items, purged items replaced by a one-line stub (never silently deleted), never purge user messages / approval records / recent items, Settings toggle disables it entirely. **PLUS (user, 2026-11-15): a manual per-chat clean — a per-chat action lets the user trigger the same purge for one specific chat on demand.**
13. **Self-improvement (item 15):** drafts-only. Bots propose skill/memory drafts; the owner approves; nothing self-applies.
14. **Skills scoping (item 16):** add a minimal audience field to the skill definition (all | orchestrator). Skill 10 ships as orchestrator-only, injected only when the run's bot is the space's orchestratorBotId.
15. **Workspace folders (item 17):** 17a lists the project folders under the deployment-configured sandbox workspace root (the user's per-project-folder rule). User-added paths are a later refinement, not 17a.
16. **X reading (item 18):** build a direct JSON-fetch path — JSON APIs must never route through the rendered-page fetcher (that is the root cause of the slowness/truncation). X sources: (a) a relay base URL from deployment settings (owner-configured; profile/search/status JSON endpoints), (b) https://api.fxtwitter.com/{user} and /{user}/status/{id} as the no-key fallback for profile/status ONLY (no search/timeline/replies exist there). SSRF guard applies to the new path. Benchmark against the current path.
17. **Code Mode (item 19):** metrics priority — (1) task success rate on a fixed eval set, (2) total tokens (tool definitions + intermediate data), (3) tool-call count, (4) wall time. HARD constraint: approval-gated tools are excluded from the code surface or pause for the same ask; a design that can bypass approvals is an automatic reject.
18. **General keys (item 20):** design doc evaluates shared vs separate passwords; verifier recommendation = separate unlock scope on the same vault service/UX (grant scopes stay separate even if the user later chooses one password). Implementation gated on design approval.
19. **EIP-1193 (item 21) v1 scope:** eth_requestAccounts (approval-gated), eth_accounts, eth_chainId, personal_sign (approval-gated), eth_sendTransaction ONLY via the PR 6/7 proposal+confirm path. eth_signTypedData_v4 is OUT of v1.
20. **Ripwire (item 23):** no app code. It is a builder-workflow CLI (tree-sitter call graph: --for / --impact / --callers / --edit-check). AutoClaw's part: if it can install the prebuilt binary in its own environment, use it for orientation on large PRs and note usefulness in PR reports. No branch, no PR.
